# Tsumugi 設計メモ

言葉を紡ぐ、ローカル LLM 内蔵の日本語入力メソッド (macOS)。

## 1. 誰の、どんな困りごとを解くか

**想定する人**: 毎日 Mac で日本語を大量に書く人。メール、チャット、ドキュメント、コードのコメント。

観察される困りごと (共感 → 問題定義):

| 場面 | 困りごと | 本当に欲しいもの |
|---|---|---|
| 同音異義語 (こうせい・こうえん) | 文脈を見ればわかるのに、毎回スペースを連打して選ぶ | 文脈を読んで最初から正しい字が出る |
| 定型の言い回し (お世話になっております) | 何百回も同じ文を全部打つ | 打ち始めたら続きを出してくれる |
| 自分だけの語彙・人名 | 一度直しても次にまた間違える | 一度直したら二度と間違えない |
| 新しい IME への不安 | 打った内容がどこかへ送られていないか | 端末の外に一切出ないと言い切れる |

**問い**: どうすれば「考える速さで書ける」状態を、入力内容を端末の外に出さずに作れるか。

## 2. 体験の原則

1. **手を止めさせない** — 打鍵から表示まで体感ゼロ。LLM の結果を待って表示が遅れることがあってはならない。
2. **ちらつかせない** — 目の前の文字が理由なく変わると不安になる。LLM の見直しは「最初からその結果で出す」。
3. **提案は控えめに、採用は 1 キーで** — 先読みは確信があるときだけ出す。採用は Tab、無視はそのまま打ち続けるだけ。
4. **一度教えたら忘れない** — 自分で選び直した変換は、LLM より辞書より優先する。
5. **端末の外に出さない** — 変換も学習もすべてローカル。学習は止められ、消せる。
6. **慣れた操作を壊さない** — Space・Enter・矢印・F6〜F10 は既存の日本語入力と同じ意味。

## 3. 操作の流れ

```
未入力 ──打鍵──▶ 入力中 (ライブ変換) ──Space/矢印──▶ 候補選択
  ▲                │  Enter: 確定                    │ Enter: 確定 (選び直しを学習)
  │                │  Tab:   先読みを確定             │ Esc:   入力中へ戻る
  └────────────────┴─────────────────────────────────┘
確定の直後: よく続けて入力する句があれば先読みを表示 (Tab で確定)
```

| キー | 入力中 | 候補選択中 |
|---|---|---|
| 文字 | 打ったそばから漢字に変わる | いまの変換を確定して次の入力へ |
| Tab | 先読みを確定 | 次の候補 |
| Space / ↓ | 候補を開いて次の候補へ | 次の候補 |
| Shift+Space / ↑ | — | 前の候補 |
| ← → | 文節を選ぶ | 文節を移動 |
| Shift+← → | 文節を縮める / 伸ばす | 同じ |
| 1〜9 | (数字を入力) | その番号の候補を選ぶ |
| Enter | 確定 | 確定 |
| Esc | 先読みを消す → もう一度で入力を取り消す | 入力中へ戻る |
| F6 / F7 / F10 (Ctrl+J / K / L) | ひらがな / カタカナ / 英数 | 同じ |
| 英数 / かな | 直接入力と日本語入力の切り替え | — |

先読みピルの左のアイコンで出どころがわかる: 時計 = 自分の履歴、きらめき = LLM の予測。

## 4. 構成

```
┌──────────────── TsumugiIME (InputMethodKit) / TsumugiPlayground ────────────────┐
│  キーイベント → KeyMapping → Session.handle(key) → SessionView → 未確定文字列 + パネル │
└───────────────────────────────────┬───────────────────────────────────────────┘
                    TsumugiCore (純 Swift・UI 非依存)
   Composer ─ ローマ字 → かな
   Converter ─ ラティス + Viterbi、後ろ向き A* の N-best、LLM 出力の検証 (match)
   SystemDictionary ─ Mozc OSS 辞書を独自バイナリ化して mmap (約 129 万語 / 63MB)
   UserModel ─ 選び直した変換・確定した句・句のつながり・読みの並び (書き癖) を学習 (JSON 1 ファイル)
   Session ─ 状態機械。辞書の結果を即表示し、LLM を締め切りつきで待つ
                    TsumugiLLM
   ZenzModel ─ zenz-v3.2-small (GPT-2 系 約 9 千万パラメタ, 74MB) を llama.cpp で実行
```

### 変換は「辞書が土台、LLM が見直し、ユーザーが最終決定」

1. **辞書 (同期, 1〜10ms)**: 読みからラティスを作り、単語コスト + 接続コストの最小経路を Viterbi で求める。
2. **LLM (30ms の締め切りつき)**: 左文脈と読みを zenz に渡して変換させ、その出力が **ラティス上で読みと一致するか検証** してから採用する。
   LLM が読みと無関係な文字を作っても表示には出ない。辞書にない英字表記 (ChatGPT など) だけは対応づけを緩めて通す。
3. **ユーザー**: 自分で選び直した語が含まれる文節は、LLM の結果で上書きしない。

締め切りに間に合えば最初から LLM の結果を表示し (ちらつきなし)、間に合わなければ辞書の結果を出して後から差し替える。

### LLM を打鍵ごとに間に合わせる工夫

読みは 1 打鍵で 1 文字しか伸びないので、前回の出力の大半は今回も正しい。前回の出力を「当て推量」として
プロンプトに続けて **1 バッチで評価** し、モデルの選択と一致するところまでを一気に採用、食い違った位置からだけ生成し直す。
KV キャッシュの接頭辞再利用と合わせて、1 トークンずつ生成する場合の数分の一で済む。

### 先読み (Tab 補完) の出どころ

| 優先 | 出どころ | 条件 |
|---|---|---|
| 1 | 履歴: 打ちかけの読みで始まる、過去に確定した句 | 3 文字以上打った / 2 文字なら 2 回以上・1 文字なら 4 回以上使った句 |
| 2 | 履歴: 直前の確定のあとによく続く句 (確定直後) | 2 回以上、かつ半分以上の割合で続いている |
| 3 | LLM + 書き癖: zenz に読みの続きを 1 文字ずつ予測させ、変換して表示 | 1 文字ごとの確率 0.4 以上、積 0.2 以上、2 文字以上伸びる (確定直後は 0.45 以上) |

LLM の予測は句読点・確信のない文字の手前で止めるので、言い切れるところまでしか出ない。

### LLM に渡す手がかりを増やす

LLM の先読みは「何を見せて予測させるか」で決まる。モデルを大きくするより、次の 2 つが効いた。

1. **入力先の文章を読む**: カーソルより前の文章 (最大 300 字) を入力先のアプリから受け取り、左文脈にする。
   自分が打っていない文章 (返信先の本文、書きかけの文書) に出てきた語も先読みに出る。zenz には末尾 100 字を渡す
   (40 → 80 字で的中が上がり、それ以上は変わらなかった)。文章を教えてくれないアプリでは、これまでどおり自分が確定した文字列をつなぐ。
   受け取った文章はメモリ上で文脈に使うだけで、保存しない。
2. **書き癖を混ぜる**: 確定した読みを、続けて打ったまとまりごとに記録しておく (最大 3 万字)。zenz が次の 1 文字を選ぶたびに、
   「直前の読み 3〜8 文字が一致する過去の箇所で、次に何を打ったか」を引き、`(1 - w) × LLM の確率 + w × 自分の割合` で混ぜる。
   重み w は、一致が長く、回数が多いほど大きい (最大 0.85)。句の履歴 (上の 1・2) は確定の区切りが同じときしか効かないが、
   こちらは読みの並びなので、区切りが違っても、別の文の途中でも効く。社名・製品名・自分の決まり文句を LLM が言い切れるようになる。

### 学習

| 覚えるもの | きっかけ | 効き方 |
|---|---|---|
| 読み → 表記 | 候補を自分で選び直して確定 | ラティスに専用ノードとして参加。回数に応じて 3000〜7000 のコスト優遇 (60 日で半減) |
| 確定した句 | すべての確定 | 打ちかけからの補完 |
| 句のつながり | 30 秒以内に続けて確定 | 確定直後の先読み |
| 読みの並び (書き癖) | すべての確定 | LLM の先読みに 1 文字ごとに混ぜる |

保存先は `~/Library/Application Support/Tsumugi/user_model.json` (パーミッション 600)。入力メニューから一時停止と全消去ができる。
パスワード欄では macOS がセキュア入力に切り替えるため、入力メソッド自体が呼ばれない。

## 5. 検討して選んだこと

| 論点 | 選択 | 理由 |
|---|---|---|
| 変換コア | 自作 (辞書データのみ Mozc OSS) | 仕組みを自分のものにでき、LLM・学習との組み合わせ方を自由に決められる。コアは Session の裏にあり差し替え可能 |
| LLM | 変換特化の zenz 1 本 | 実測で変換 10〜30ms、続きの予測も同じモデルでできた。先読み専用に大きい LLM を足す案は実測して見送った (下の「試して採らなかったこと」) |
| 推論 | CPU (性能コア 4 スレッド) | このサイズでは GPU より立ち上がりが速く安定 (GPU は初回 400ms 超) |
| LLM の出力の扱い | ラティスで検証してから採用 | 小さなモデルの作り話を画面に出さない |
| 先読みの見せ方 | カーソル下の小さなピル | 他アプリの文字の上に薄い文字を重ねることは入力メソッドからはできない。位置が動かず視線を奪わない |
| 文末での自動確定 | しない | 確定後は直せないため、確定は必ず利用者の操作で |
| 未入力時の数字・記号 | そのままアプリへ渡す | 「2026」のたびに Enter を押させない |

### 試して採らなかったこと (先読み)

| 案 | 結果 |
|---|---|
| 先読み専用に汎用の日本語 LLM (sarashina2.2-0.5b, Q4 で 528MB) を足す | 正解の文を当てるのに要る情報量が zenz と変わらなかった (1 かなあたり zenz 1.63 bit / sarashina 2.07 bit、長い文脈に頼る文書でも 1.86 / 1.84)。速度は足りた (16 トークン 約 130ms) が、容量 3.7 倍に見合う伸びがない |
| macOS 内蔵のオンデバイス LLM (FoundationModels) | 応答まで約 0.9 秒。確率が取れないので「確信があるときだけ出す」ができない |
| 確信の固い所までを Tab 1 回、その先を次の先読みに残す二段表示 | 省打鍵・的中とも変わらず。外れる先読みは最初の分かれ目で外れていて、頭だけ正しいものは少なかった |
| 書き癖の重みを強くする | 癖のある文書では伸びるが、癖のない文書で外れが増えた (打鍵 29% 減 → 26% 減) |

## 6. 先読みの計測

`tsumugi-cli eval` が、文書を頭から打鍵し、正しい先読みが出たら Tab で受け入れる利用者を模して測る
(3 打鍵以上省けるときだけ受け入れる)。コーパスは `Tools/eval/` にある。先読みを変えるときは、まずこの数字で比べる。

| 条件 | 打鍵の削減 | 出した先読みの的中 |
|---|---|---|
| 一般的な文書 10 本・学習なし (変更前: 文脈 40 字) | 29.0% | 57% |
| 同上 (文脈 100 字) | 29.8% | 59% |
| 書き癖のある文書 3 本・似た文書 3 本を書いたあと (書き癖なし) | 40.2% | 51% |
| 同上 (書き癖あり) | 45.2% | 63% |

コーパスは定型的な文が多く、数字は実際の利用より高めに出る。案どうしを比べる物差しとして使う。
入力先の文章を読む効果は、この計測には入っていない (計測では常に自分の確定だけが文脈になる)。

## 7. 読み直し (確定後の直しの提案)

書いたあとに読み返して直す手間のうち、機械的に直せる部分を入力メソッドが引き受ける。
何を直すかは、利用者本人が過去に打った文章 538 文を読んで決めた。実際にあった誤りは次のとおり。

| 誤りの種類 | 件数 | 例 |
|---|---|---|
| 同音の取り違え・変換し忘れ | 約 15 | 仕様率 (使用率)、分に (文に)、売って (打って)、じょうで (上で) |
| 打ち間違い | 約 6 | おお願い、フォマローアップ |
| 助詞の誤り | 1〜2 | 構成も変えることも |

助詞を省く書き方 (「ブラウザ使ってみて」) は数多いが、これは口調であって誤りではない。

### しくみ

打っている最中の変換は、その時点までの読みしか知らない。句ごとに確定していくと、あとに続く言葉で決まるはずの
同音異義語を取り違えたまま残る。そこで、確定して手が止まったら、いまの文を **文全体の読みで変換し直す**。

1. カーソルより前の文章から最後の文を取り、かな・漢字が続く範囲ごとに読みを推定する (OS の形態素解析)。
2. その読み全体を zenz で変換し直す。結果が元と同じなら何もしない。
3. 違う箇所ごとに、そこだけ差し替えた文を採点する。「その読みがその表記になる確からしさ」と「文章としての自然さ」の
   両方が大きく上がるときだけ提案する (対数確率で +3 以上かつ +2 以上)。
4. 変換し直した結果が元の読みで読めることを、ラティスで検証する (モデルの作文を出さない)。

反映は、直す箇所からカーソルまでをまとめて置き換える (カーソルを動かさないため)。置き換える前に入力先の文章が
提案時と同じか確かめ、置き換えた後にも文章とカーソルの位置を読み直して、想定どおりでなければそのアプリでは以後提案しない。

Electron 系のアプリには癖が 4 つあり、実機で確かめて合わせた (4 つめ: カーソルの手前 100 字を超える範囲の文章を尋ねると何も返さない。Notion で位置が 110 字を超えると 261 回続けて読めなかった。300 → 100 → 60 → 30 字と狭めて尋ね直し、途中から始まる先頭の語は読み直さない)。

- 長さ 0 の範囲の矩形を尋ねると画面の外を返す。カーソルの位置は直前の 1 文字の矩形から求める。
- 範囲を指定した書き換えだけだと「入力メソッドはこのキーを使わなかった」とみなし、Tab をアプリ側でも処理する
  (フォーカスが隣の欄へ移る)。末尾の 2 文字だけを、ふつうの確定と同じ形で入れると、キーは使われたものとして扱われる。
- 未確定文字列として差し替える方法 (再変換の手順) は、範囲の指定が無視されて末尾に足されるので使えない。

### 計測

`tsumugi-cli proofread <1 行 1 文のファイル>` で測る。

| 文章 | 提案 | 内訳 |
|---|---|---|
| 利用者本人の過去の文章 538 文 (しきい値を決めるのに使った) | 13 件 | 正しい直し 10、誤りの場所は合っているが直し方が違う 2、誤提案 1 |
| 同じ人の別の文章 2,160 文 (しきい値を決めたあとで測った) | 84 件 | 正しい直し 47、場所は合っているが直し方が違う 10、表記の好み 24、誤提案 3 |
| 誤りのない文 103 行 (`Tools/eval/corpus*.tsv`) | 0 件 | — |
| 誤りを 8 件仕込んだ見本 20 文 (`Tools/eval/proofread.txt`) | 7 件 | すべて正しい直し。誤りのない 12 文への提案は 0 |

「表記の好み」は「みて → 見て」「後 → あと」のように、どちらでも誤りではないもの。3 回見送れば出なくなる。
「誤提案」は正しい文を壊す直しで、2,160 文に 3 件 (「とかは行ってから → とか入ってから」など)。

`--inject` を付けると、文末の語を同じ読み・同じ品詞の別の語に差し替えて、見つけて元に戻せるかを測る。
2,160 文のうち差し替えられた 1,392 文で、しきい値を振った結果:

| 伸びのしきい値 (読み / 自然さ) | 仕込んだ誤りを元に戻せた割合 | 2,160 文への提案: 正しい直し / 表記の好み / 誤提案 |
|---|---|---|
| +2 / +2 | 70% | 48 / 26 / 3、ほかに未判定 30 |
| **+3 / +2 (採用)** | 69% | 47 / 24 / 3 |
| +4 / +2 | 66% | 42 / 11 / 3 |
| +5 / +2 | 62% | 36 / 3 / 3 |

しきい値を上げると表記の好みは減るが、正しい直しも一緒に減る (+3 → +4 で好み 13 件と引き換えに直し 5 件)。
好みの提案は見送れば消えるので、直しを多く拾うほうを採った。下げても正しい直しはほとんど増えない。
誤提案はしきい値では減らせなかった。

過去の文章にはスマホで打ったものも混じる。英数字の前後に空白を入れるかどうかで端末を見分けられた
(端末の印が残っている文で、Mac は空白あり 19 / なし 5、スマホは 1 / 24)。空白ありの 1,227 文だけに絞っても
提案 52 件のうち正しい直し 32・場所は合うが直し方が違う 5・表記の好み 13・誤提案 2 で、傾向は変わらない。
2,160 文のほうは端末 (CLI) の入力履歴で、ほぼ Mac で打ったもの。

実機では、テキストエディットと Electron (入力欄とチャット欄と同じ方式の編集領域) の両方で、句ごとに確定して
「しよう」「率が高い」と打つと「しよう率 → 使用率」がカーソルの下に出て Tab で置き換わること、
過去の文「if 分が入ることは…」で「分が → 文が」が出て置き換わること、置き換えのあともカーソルとフォーカスが
動かず続けて打てること、誤りのない文には何も出ないことを確かめた。
さらに過去の文 16 件 (誤りを含むもの 13、正しいもの 2、誤提案が出ると分かっているもの 1) を Electron の編集領域に入れて
本物の入力経路で確定したところ、提案の有無と直した結果は 16 件とも `tsumugi-cli proofread` の結果と一致した
(守護 → 主語、以降 → 移行、その編 → その辺、本島に → 本当に、仕様率 → 使用率、買いて → 書いて など 7 件を置き換え)。

本人の文章は私的な内容を含むのでリポジトリには入れていない。読みを推定に頼るぶん、「3 強かな」を「したたか」と
読むような取り違えが起きるが、しきい値でほぼ落ちる。

### 試して採らなかったこと (直し)

| 案 | 結果 |
|---|---|
| 助詞を 1 つずつ別の助詞に入れ替え、文章としてより自然になるものを提案する | 同じ 538 文で 264 件の提案が出て、本当の誤り (1 件) は上から 12 番目。上位は「何を → 何も」「は → が」など意味を変える入れ替えばかりだった |
| 余分な言葉 (「とか」「みたいな」) を削る直しを、自然さの伸びで判定する | 文は短いほど確率が高く出るので、削ればほぼ必ず「自然になった」と出る。1 文字あたりに直すと勝ち負けがばらついた |
| 自然さの低い文字を誤りの場所とみなす | 誤りの助詞は確かに低い (0.00〜0.01) が、名詞や動詞の出だしも同じくらい低い。何の話をするかは予測できないため |
| かな ↔ 漢字の表記の違い (みやすい / 見やすい) を誤りと区別する | 確からしさの伸びでは分けられなかった。見送った提案を覚えて繰り返さないことで対処した |

## 8. 実測 (M3 / 8GB)

| 項目 | 値 |
|---|---|

## 9. いまの限界と次の一手

- 直しの提案は同音の取り違えと変換し忘れだけ。助詞の誤り、重複、打ち間違いは拾えない (変換特化のモデルでは判定できなかった。上の表)。
- 直しの提案は、文章を読めて、範囲を指定した置き換えを受け付けるアプリでだけ働く。確かめたのはテキストエディットと Electron の素の入力欄、それに Notion (0.2.3 で提案と反映が記録に残ることを確認)。

- 数字・日付・単位・顔文字などの特殊変換は未実装 (辞書にある範囲のみ)。
- 入力中のカーソル移動による途中編集はできない (文節単位の操作のみ)。
- 確定後の再変換、ユーザー辞書の手動登録 UI は未実装。
- 候補パネルはキーボード操作のみ (クリック不可)。
- 候補パネル (9 行、高さ約 270pt) は、下に収まらないときカーソルの上に出る。画面の下端にある入力欄 (チャット欄など) では、
  それまでに書いた行のうちカーソルの真上の幅 140pt ぶんを覆う。文字が消えたように見えるが、入力中の文字は保たれている。
- 先読みは最有力の 1 本だけ。分かれ目 (「〜がありましたら / 〜がございましたら」) で外れるぶんは、第 2・第 3 候補を並べれば拾える。
- 入力先の文章はカーソルより前だけを読む。後ろの文章や、アプリの種類 (メール・チャット・エディタ) は見ていない。
- 学習データが増えたときの「文体に合わせた LLM の個人化」は、zenz v3 のプロフィール条件 (タグ U+EE03) を使えば拡張できる。
